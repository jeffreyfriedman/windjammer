# ADR-0031: The interpreter calls Rust crates through a cached crate host process

- **Status:** Proposed (vertical slice implemented: strsim, shlex, crc32fast and a path crate with every surface shape)
- **Date:** 2026-11-04
- **Related:** [ADR-0022](0022-interpret-by-default.md) (interpret by default), [ADR-0023](0023-interpreter-rust-crate-bridge.md) (host bridge for `extern fn`),
  [ADR-0026](0026-rust-crate-dependencies.md) (crate dependencies and signature surfaces; this is its ladder rung 3),
  [ADR-0021](0021-effects-and-capabilities.md) (capabilities, effect port, durable), `src/interpreter/crate_host/`, `src/cli/crate_host_build.rs`,
  `tests/interpreter_rust_crates_test.rs`

## Context
ADR-0026 made a Rust crate a first-class dependency: list it in `wj.toml`, a signature surface (generated by
`wj rust-surface` from the crate source, or hand-written in `rust/<crate>.wji`) declares the callable functions in
Windjammer types, `wj check` checks calls against it and `wj build` compiles them. The interpreter stopped at the
first such call: `wj run --interpret` exited 2 with `not interpreted yet: call into Rust crate dependency ...
[deps.rust_crate]` and `wj run` fell back to a full compiled build of the program. A project that uses one
crate function therefore lost the interpreted-first loop (instant start, `--record`/`--replay`, `--simulate`,
`--limits`, hot reload), which is the loop agents prefer.

What already existed (survey, `next/v0.50.0` at `f981703fd`):

| Piece | Where | What it gives |
|---|---|---|
| Host bridge for `extern fn` | `interpreter/host_bridge.rs`, `cli/host_build.rs` (ADR-0023) | A `cdylib` per project, built once into `<cache>/host/wj_host_<hash>/` with its **own** target dir (about 300 MB each today), loaded with `libloading`, C-ABI shims over int/float/bool/string only. No crash isolation: a panic across `extern "C"` aborts the interpreter. |
| C library calls | `interpreter/c_library.rs` | Scalar `extern fn` in the process's C library. |
| std modules | `interpreter/builtins/std_*.rs` | Native Rust in the `wj` binary itself: the only way `std::net` and friends reach real code. Not extensible by a project. |
| Effect port | `interpreter/effect_port/` | One choke point for every sink: `--record` logs (JSON values via `codec.rs`), `--replay` answers from the log, `--simulate` answers from a seeded world. |
| Capability gate | `interpreter/caps.rs` | `cap_decide(effect, resource)` before a sink; denial is exit 126. |
| Surfaces and effects | `package/rust_surface*.rs`, `ir/effect_facts/crates.rs` | Function list, Windjammer types, `@pure`/`@uses`, otherwise `ffi(<crate>)`. |
| Durable steps | `check/durable_sites.rs`, `interpreter/durable_rt.rs` | Every call with an effect inside a `durable fn` is a journaled step, found by the static effect pass (which already attributes `ffi(<crate>)`). |

## Options
### A. A host process per crate set, generated from the surfaces
A small cargo binary with one shim per surfaced function, built once and cached by a hash of {crate versions from
the lock file, surface text, dependency lines, generator version}; the interpreter spawns it on the first crate
call, keeps it for the run and speaks a length-prefixed binary protocol over two pipes.
- Pros: crash isolation (a crate `abort`, stack overflow or segfault kills the host, and the interpreter reports
  it with the function name); panics caught with `catch_unwind` in the host; no `unsafe` value layout shared
  across a C ABI: values are serialized, so nested `Vec`/`Option`/`Result`/tuples cost nothing extra to support;
  the crate's stdout and stderr are the program's (fds 3 and 4 carry the protocol); a host could later run under
  its own OS sandbox profile (the capability model's natural next step); hosts of different programs share
  one cargo target directory, so a crate version is compiled once per machine and each host keeps only its binary.
- Cons: a round trip per call (pipe write + read + two context switches: tens of microseconds, measured below);
  a process per run (spawned lazily, only when a crate function is actually called).

### B. A generated `cdylib` loaded in-process (`dlopen`), the ADR-0023 path extended
- Pros: a call is a function call (about 100 ns); the loader exists.
- Cons: every value shape needs a C-ABI mirror or an in-memory encoding anyway (so the marshalling work is the
  same as A, minus the pipe); no isolation: a crate that aborts, overflows its stack or corrupts memory takes the
  interpreter down, which breaks the rule that a crate failure is a normal interpreter error; `panic = "abort"`
  crates or `extern "C"` panics are process-fatal; two crate versions or two `std` copies in one process need
  care; unloading is unsound in general, so hot reload cannot swap a host.
- Path: B is the right **fast tier** for hot pure numeric functions once A is the semantics (same generator,
  a second backend). Kill criterion for doing it: a measured program where crate-call overhead is above 20% of
  run time under A.

### C. A wasm component per crate set
- Pros: strong isolation with no process, deterministic by construction (no ambient clock, fs or network unless
  imported), portable host caches, and the capability model maps directly onto component imports.
- Cons: many crates do not build for `wasm32-wasip2` (anything with `libc`, threads, native deps); needs a wasm
  runtime in `wj` (wasmtime is about 15 MB and long to build); the compiled path is native, so equivalence
  becomes "native result == wasm result" (float formatting and `usize` width differ on wasm32).
- Path: prerequisite is a wasm runtime already being in `wj` for another reason (the browser/edge targets);
  first experiment: build the strsim host for `wasm32-wasip2` from the same generator and compare its outputs on
  the drift corpus. It is the best long-term answer for `--sandbox` runs of untrusted crates.

### D. In-process JIT of only the surfaced calls
Compile the crate functions themselves to machine code inside `wj` (Cranelift over MIR, or rustc as a library).
- Pros: no cargo step at all for the user; calls as fast as B.
- Cons: needs rustc's front end (stable rustc exposes no such API; `rustc_private` ties `wj` to one nightly), or a
  Rust-to-Cranelift compiler for arbitrary crate code, which is a Rust compiler. Not reachable incrementally.
- Path: track `rustc_codegen_cranelift` and a stable `rustc` driver API; the generator and the wire format of A
  stay valid as the boundary, so D would replace only how the host is produced.

## Decision: A
A gives the properties the interpreter promises (a crate failure is an error, never a crash; replay never runs
the crate; the interpreted result equals the compiled result) with the least new unsafe code, and its generator
is reusable by B and C later. The per-call cost is small next to what users call crates for, and it is measured
here so the B tier can be justified by data rather than guessed.

### How a call runs
`strsim::levenshtein(a, b)` in the interpreter, in order:
1. **Preflight** (`interpreter/preflight.rs`): a call into a crate the host serves is accepted; a crate function
   the surface does not declare, or whose types cannot cross, keeps the `deps.rust_crate` report (so `wj run`
   still falls back to compiled and `--interpret` exits 2 naming the function).
2. **Capability gate** (`crate_host/mod.rs`): `@pure` needs nothing, `@uses(..)` is checked effect by effect, anything
   else is `ffi(<crate>)`, checked against `[capabilities] ffi = ["<crate>"]` / `--allow ffi=<crate>`. This runs
   before any byte is sent; a denial is exit 126 (`--caps enforce`), exactly as for a std sink.
3. **Effect port**: `--record` performs the call and logs `ffi strsim::levenshtein(args) -> result` (the result
   includes the copied-out `&mut` arguments, and a panic is logged as an error); `--replay` answers from the log
   and never starts the host; `--simulate` runs `@pure` functions (they are functions of their arguments) and
   answers every other function from `fixtures/rust_stubs.json` (`{ "shlex::split": ["a", "b"] }`, plain JSON read
   by the surface type), or stops with exit 2 naming the function and the stub file.
4. **Host call** (`crate_host/process.rs`): arguments are encoded by their surface types, the program's buffered
   stdout is flushed (so output order matches the compiled program, where the crate prints to the same stdout),
   one request frame goes out, one reply frame comes back.
5. **Result**: decoded by the declared return type (an `usize` result is an interpreter `usize`), `&mut`
   arguments written back to their places.

Durable functions need nothing new: the static pass already marks a call with effect `ffi(<crate>)` as a step,
and the journal records its result like any other step.

### Wire format (`crate_host/wire.rs`, host side generated by `crate_host/gen.rs`)
Frames are `u32` length + body. Values are self-describing, little-endian: tag byte, then payload: unit 0,
integer 1 (`i128`), float 2 (`f64` bits; `f32` widened exactly), bool 3, char 4 (`u32`), string 5 (`u32` length +
UTF-8), `Vec` 6 (count + items), `None` 7, `Some` 8, `Ok` 9, `Err` 10, tuple 11 (count + items). Both sides check
each tag against the declared type, and the host checks integer ranges (`u8::try_from`), so a mismatch is an error
naming the function, never a misread. Request: function path (string) + arguments. Reply: status 0 + count +
values (result, then `&mut` arguments), status 1 + panic message (with the crate's file and line), status 2 +
rejection. The host's first frame is its cache key; a binary that announces another key is refused.

### Marshalling of the surface type language
| Surface | Rust parameter in the shim | Notes |
|---|---|---|
| `i8`..`u64`, `usize`, `isize`, `int`, `float`, `f32`, `bool`, `char` | the same type, owned | range-checked on decode |
| `string` | `&str` (decoded `String`, passed `&a0`) | ADR-0026 convention: string parameters are borrowed |
| `Vec<T>`, `Option<T>`, `Result<T, E>`, tuples (up to 6) | owned, recursively | `Result<_, String>` errors arrive as values |
| `&T` (incl. `&Vec<u8>` for Rust `&[u8]`) | decoded `T`, passed `&a0` | deref coercion does `&Vec<T>` to `&[T]`, as in the compiled call site |
| `&mut T` | decoded `T`, passed `&mut a0`, sent back | copy-in/copy-out; the interpreter writes the place (`v` or `&mut v` at the call site) |
| crate types (`Regex`, `Cow<str>`) | not yet | next rung: opaque handles (below) |

The shim writes the declared return type on its binding (`let r: usize = ::strsim::levenshtein(&a0, &a1);`), so a
surface that disagrees with the crate fails the host build exactly where it would fail the compiled build.

### Panics, crashes, exits
A crate panic is caught in the host and becomes an interpreter panic (exit 101, the compiled program's status)
with the message `Rust crate function `shapes::boom` panicked at src/lib.rs:12:31: boom: x`. A host that dies
during a call (signal, abort) is an interpreter panic naming the function and the signal; the next call starts a
fresh host. A crate that calls `std::process::exit(n)` ends the interpreted program with `n`, as compiled.

### Cache, cold start, disk
- Key: FNV-1a over the `wj` version, generator version, the generated shim source (every surfaced signature of the
  crates the program names), the `wj.toml` dependency lines of those crates and their locked versions.
- Layout: `<cache>/host/crates/<key>/{Cargo.toml, src/main.rs, wj-crate-host}` and one shared
  `<cache>/host/crates-target/`. The lock file next to `wj.toml` (or `build/Cargo.lock`) is copied in, so the host
  uses the versions the compiled build uses. `cargo build --release --offline` first (the local registry; no
  network), then online if something is missing.
- Measured (this machine, 10 concurrent agent builds, `CARGO_BUILD_JOBS=2`): see "Measurements".

### Equivalence
The rule is ADR-0022's: the interpreted result must equal the compiled result. `tests/interpreter_rust_crates_test.rs`
runs each fixture project both ways (`wj run --interpret` and `wj build` + `cargo run` of the generated crate)
and compares exit status and stdout, plus textbook values as a second oracle. A mutation check rebuilds the host
with `levenshtein` off by one and asserts the comparison fails.

## Ambition ladder
1. **Done (this ADR):** free functions over the surface type language, any number of crates per program, panics,
   record/replay, simulate with `@pure` or stubs, grants, durable steps, copy-in/copy-out `&mut`.
2. **Opaque handles** (ADR-0026 rung 4, designed here): a surface declares `pub struct Regex` (no fields) and
   functions or methods over it (`fn new(p: string) -> Result<Regex, string>`, `fn is_match(self: &Regex, s: string) -> bool`).
   The host keeps a table `u64 -> Box<dyn Any>`; a handle crosses as tag 12 + `u64`; the interpreter holds it as a
   `Value::Native` whose drop sends a release frame (batched), so lifetimes follow Windjammer ownership. `&self`
   methods borrow from the table, `self` methods remove the entry. Record/replay logs handles as opaque ids
   (a replayed handle is only ever passed back to replayed calls); simulate needs stubs for constructors. First
   experiment: `regex::Regex` (`new`, `is_match`, `find` returning `Option<(usize, usize)>`).
   Kill criterion: handle-churn programs where release traffic exceeds 30% of calls; then batch on scope exit.
3. **Monomorphised generics** in the generator (`AsRef<str>`, `AsRef<[u8]>`, `impl Into<String>`) so hex, base64
   and friends map, and an owned-`String` parameter form.
4. **Callbacks** into interpreted closures (`sort_by`, visitors): a reverse request frame on the same pipe while a
   call is in flight (the host blocks on the interpreter's answer). Needs re-entrancy in the protocol only.
5. **`wj test --interpret`** and the REPL use the same host (today `wj run` builds it).
6. **Fast tier (option B)** for `@pure` scalar functions whose per-call cost dominates, behind the same
   generator, gated by the equivalence tests; **sandboxed host** (`sandbox-exec`/seccomp profile per grant) and
   **wasm hosts (option C)** for untrusted crates.
7. **No cargo for registry crates**: a shared, signed cache of prebuilt hosts keyed by the same hash (CI builds
   popular crate sets), so a cold start is a download.

## Consequences
- `wj run` on a project that calls surfaced crates stays interpreted; the first run builds the host once.
- The interpreter spawns a process (the host binary), never cargo; `cli::crate_host_build` runs cargo.
- `docs/INTERPRETER.md` and `docs/MODULE_SYSTEM.md` describe crate calls as interpreted.

## Decision needed from: project owner
Accept option A as the semantics of interpreted crate calls (with B and C as later tiers behind the same generator),
the `fixtures/rust_stubs.json` stub format for `--simulate`, and the handle design for the next rung.
