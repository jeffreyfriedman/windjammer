# Results: Windjammer-generated Rust vs idiomatic Rust

Produced by `scripts/wj/rust_parity_run.wj` (10 kernels, `--runs 11`) and rendered by `scripts/wj/rust_parity_report.wj`;
raw data in `benchmarks/rust_parity/results.json`. Variants per kernel:

- baseline: compiler output WITHOUT the post-codegen optimizer (snapshot `generated_baseline/*.rs`,
  generated by the pre-change `wj`);
- optimized: `optimize_rs(baseline)`, byte-identical to what the compiler hook emits now;
- idiomatic: hand-written Rust (`rust/*.rs`) with identical output (checked by the harness).

All built with `rustc -C opt-level=3`. Allocation counts come from a counting `#[global_allocator]`
build of the same source. Source counts are `grep`-style counts on the source text.

## Conditions and limits (read before quoting anything)

- Machine: macOS arm64, shared with ~8 other build/test jobs during the run. CPU frequency cannot be
  pinned on macOS. Wall-clock samples are therefore dominated by scheduling noise (see the min..max and
  stdev columns: stdev is often larger than the median). `cpu` (user+sys of the child, median of 11) is
  the usable timing column; differences below ~0.01 s CPU are noise.
- The WJ kernels needed type annotations or rewrites to avoid compiler inference bugs
  (`docs/known-issues/`); the HashMap kernel was replaced by a Vec histogram.
- Ten micro-kernels say nothing about large programs, I/O, or compile time. No "x% of Rust" figure
  is claimed here; none is supported by this data.

## What the data supports

- Pure compute kernels (collatz, fib, sieve, nbody, byte_hash, histogram, insertion_sort, matmul): CPU
  medians of baseline, optimized and hand-written agree within noise (collatz 0.477 / 0.478 / 0.473 s,
  fib 0.128 / 0.129 / 0.130 s, matmul 0.028 / 0.027 / 0.024 s). The generated loops compile to the same
  code as idiomatic Rust; the optimizer is not what makes them fast and does not need to.
- Where the optimizer changed behaviour:
  - string_build (`out = format!("{}{}{}", out, w, ",")`): allocations 120016 -> 40022, bytes allocated
    13221 MB -> 1.9 MB, CPU 0.186 s -> 0.004 s (hand-written 0.004 s). Quadratic to linear.
  - `Vec::new()` + push loops: allocations sieve 28 -> 6, matmul 53 -> 8, vec_fill 805 -> 45, histogram
    16 -> 6, nbody 10 -> 6 (all equal the hand-written counts); CPU vec_fill 0.202 -> 0.126 s.
- Remaining gaps vs hand-written Rust:
  - vec_fill CPU 0.126 s vs 0.042 s although allocations are equal: the generated `for i in 0..v.len() { s += v[i] }`
    plus `as u64` casts vs iterator `sum`/`collect`. Cause not isolated; no pass addresses it.
  - insertion_sort (19 vs 6 allocs) and byte_hash (26 vs 6): the `Vec::new()` is separated from its push
    loop by a non-Vec `let` (`let mut x = ..`), which the pass does not skip. CPU is equal anyway.
- Binary sizes are identical to within 1 KB for all variants (460-480 KB).
- `.clone()` is 0 in every variant; casts drop by 0-1 per kernel.
- Wall-clock rows in this run were taken on a quieter machine than the first attempt but still carry
  large max/stdev values; do not read wall differences below ~0.05 s as signal (e.g. collatz idiomatic
  wall 2.07 s vs 1.2 s with identical CPU time).

## Corpus counts (81 files, 4712 lines; see ASSESSMENT.md section 2)

`.clone()` 18 -> 10, `#[inline]` 509 -> 438, `#[repr(C)]` 52 -> 16, `fn to_bytes` 12 -> 2,
`as` casts 42 -> 35, `format!` 21 -> 20. The ratchet test
(`tests/optimizer_ratchet_test.rs`, baseline `tests/fixtures/optimizer/ratchet_baseline.txt`) fails if
these counts grow on the fixed corpus (`tests/fixtures/optimizer/corpus`).

## Reproduce

```
cargo build --release --example optimize_rs
wj run scripts/wj/rust_parity_run.wj --optimize-rs target/release/examples/optimize_rs --runs 11
wj run scripts/wj/rust_parity_report.wj benchmarks/rust_parity/results.json
```
