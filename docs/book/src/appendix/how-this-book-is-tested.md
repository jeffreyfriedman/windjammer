# How this book is tested

Every program in this book runs. A page that shows code and output is only worth reading if the output is what the
compiler produces today, so the book's own test suite checks it.

## Examples

A fenced code block tagged `wj` is a whole program. Its test is:

1. The program runs in the interpreter and exits normally.
2. If it carries `// expect:` comments, its output equals those lines, in order.
3. The program is built and run through the compiled path, and that output equals the interpreter's.

Lines that begin with `~` are part of the program but are not shown in the rendered page. They hold the scaffolding,
such as a `fn main` around a few interesting lines. Shell blocks tagged `sh,verify` run in a scratch directory with
`wj` on the path: lines that start with `$ ` are commands, and the other lines must appear in the output, in order.

A block marked `ignore` is not run, and it needs a reason in a comment right above it. A block marked `interpreter_only`
runs in the interpreter and skips the compiled pass, for features whose compiled form is still arriving; it needs a reason
too. The number of ignored blocks and of interpreter-only blocks are each a ratchet: they can go down and never up.
Multi-file projects are shell blocks (`sh,verify`) that write their files and end with `cd DIR && wj run`; each one also
runs as a project in the interpreter and compiled, with the same agreement check.

## Reference pages

The grammar, keywords, standard library, command line, diagnostic codes and compile targets are generated from the
compiler's own tables. When a flag or a code is added, the generated page changes and the test suite fails until the
page is regenerated, so the reference cannot fall behind.

## Coverage

Every command, flag, diagnostic code and feature promise the project makes is listed in a registry. Each must be
mentioned on some page of this book; the count of unmentioned entries is a ratchet too.

## Links

Links between pages are checked, including the heading they point at. Links to files in the repository are checked
against the tree.

## When you change the language

A change to the language, a command or a diagnostic updates the book in the same change. The checks above are what make
that practical: a sample that stops compiling fails the compiler's own test run, a new flag fails until it is
documented, and the reference is regenerated by one command (`scripts/docs_gen.sh`).
