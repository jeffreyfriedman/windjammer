# Conformance

## Mapping

[CONFORMANCE_MATRIX.md](CONFORMANCE_MATRIX.md) (generated by `scripts/spec_check.sh --write`, freshness enforced) lists every `SPEC-*` rule with its example file(s). Examples live in `tests/spec/<area>/SPEC-<AREA>-<NNN>.wj`; the same code appears verbatim in the chapter next to the rule.

## What "conformant" means

An implementation conforms to a rule when the example for the rule produces exactly the `// expect:` stdout lines and exit status (or the stated parse/panic outcome). Tiers (ADR-0007, Proposed): Tier 1 must pass every rule not marked `[PLANNED]`; Tier 2 the documented subset; Tier 3 best effort.

## Current status (evidence, not claims)

- Executor used for these examples: the interpreter (`wj run --interpret`), in-process, because it needs no toolchain. It is the weakest oracle voice (docs/backends/CONFORMANCE.md), so expectations were derived independently. Running the same examples through the Rust/Go/JS/TS backends is not done yet (Q-022); the existing multi-oracle corpus in `tests/conformance_programs/` already covers many of the same semantics there and uses the same `// expect:` convention.
- Pass/fail summary: run `cargo test --release --test spec_conformance`. Examples marked `xfail` are the known divergences (see OPEN_QUESTIONS.md); every other example must pass.

## Adding a rule

1. Write `**SPEC-AREA-NNN** text` in the chapter. 2. Add `tests/spec/<area>/SPEC-AREA-NNN.wj` with `// spec:` and `// expect:` lines. 3. `scripts/spec_check.sh --write`. 4. If the implementation disagrees, add `## Q-NNN` to OPEN_QUESTIONS.md and `// xfail: Q-NNN`.
